# FinchSpeak — Отслеживание прогресса реализации

Документ отражает текущий статус разработки согласно генеральному плану ([plan.md](plan.md)).

---

## Общий статус проекта

- **Текущий этап**: Подготовка к Этапу 1 (Серверное ядро и текстовый мессенджер).
- **Выполнено**: Этап 0 (Проверка концепции, базовая спецификация, протокол, закрытие техдолга).
- **Архитектурные требования**: 100% соблюдение правил (20-байтный `MediaHeader`, SFU-перезапись `sender_peer_id`, отсутствие `unwrap`/`expect`, потокобезопасный `ringbuf`, WebCodecs без fMP4).

---

### [ ] Этап 2: Голосовая связь и аудио-движок (Недели 6–10)
- [ ] **2.1. Серверная SFU-маршрутизация датаграмм (`finch-server`)**:
  - [ ] Прием QUIC-датаграмм, валидация длины (>= 20 байт).
  - [ ] Принудительная перезапись байт 5..9 (`sender_peer_id`) на проверенный сессионный ID.
  - [ ] Веерная рассылка участникам активной голосовой комнаты с учетом флагов `deafened`.
- [ ] **2.2. Аудио-тракт захвата (`finch-audio`)**:
  - [ ] Открытие `cpal` на нативной частоте/канальности ОС, сведение в моно.
  - [ ] Связь аудио-потока ОС с Tokio через lock-free `ringbuf` (без мьютексов и аллокаций).
  - [ ] Полифазный ресемплинг в 48 000 Гц через `rubato` (`FftFixedInOut`).
  - [ ] Эхоподавление `webrtc-audio-processing` (AEC3) с референсным сигналом.
  - [ ] Шумоподавление DeepFilterNet (с фоллбэком на RNNoise / `nnnoiseless`).
  - [ ] Локальный VAD, кодирование Opus (20 мс), упаковка 20-байтного заголовка, флаг тишины.
- [ ] **2.3. Аудио-тракт воспроизведения (`finch-audio`)**:
  - [ ] Прием датаграмм, адаптивный Jitter Buffer (`seq.wrapping_sub(last_seq) as i16` -> монотонный `u64`).
  - [ ] Opus-декодер с синтезом потерянных пакетов (PLC).
  - [ ] Микшер с лимитером (`tanh`), передача референса в AEC.
  - [ ] Ресемплинг из 48 000 Гц в частоту устройства вывода `cpal`.
  - [ ] Локальный детектор речи участников для обновления UI (сервер не шлет VoiceActivity).

### [ ] Этап 3: Демонстрация экрана через WebCodecs (Недели 11–13)
- [ ] **3.1. Захват экрана и системного звука (`finch-screen`)**:
  - [ ] Захват видеокадров (xcap / Windows Graphics Capture) в BGRA.
  - [ ] Захват звука приложений (WASAPI Loopback на Windows, PipeWire на Linux).
  - [ ] Кодирование звука экрана в Opus stereo (`MediaType::ScreenAudio`).
- [ ] **3.2. Аппаратное кодирование и передача по QUIC**:
  - [ ] Аппаратное сжатие H.264 (NVENC / Media Foundation / VAAPI, фоллбэк openh264).
  - [ ] Ключевые кадры (IDR): отправка через QUIC Uni-Stream с заголовком `MediaType::VideoKey`.
  - [ ] Дельта-кадры (P-frame): нарезка на фрагменты по 1160 байт (`MediaType::VideoDelta`), отправка датаграммами.
  - [ ] SFU-маршрутизация видео подписчикам (`SubscribeScreenShare`).
- [ ] **3.3. Приемник и воспроизведение в Webview**:
  - [ ] Сборка фрагментов дельта-кадров, логика блокировки при чтении стрима IDR.
  - [ ] Запрос ключевого кадра `RequestKeyframe` при потере пакетов (с ограничением 1/с).
  - [ ] Передача H.264 NAL-единиц в Webview через `tauri::ipc::Channel`.
  - [ ] Декодирование через WebCodecs API (`VideoDecoder`) и прямой рендеринг на Canvas (без fMP4/HTTP).

### [ ] Этап 5: Сквозное шифрование (E2EE) и безопасность (Неделя 18)
- [ ] Проверка отпечатков сертификатов TOFU (Trust On First Use).
- [ ] Протокол обмена ключами X25519 для генерации комнатного ключа.
- [ ] Симметричное шифрование медиа-полезной нагрузки через ChaCha20-Poly1305:
  - Заголовок `MediaHeader` (20 байт) открыт, флаг `0x02` (E2EE), используется как AAD.
  - Nonce (12 байт): `sender_peer_id` (4Б) + `timestamp` (4Б) + `sequence` (2Б) + `frame_id` (2Б).
