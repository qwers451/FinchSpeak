# Исследование качества голоса и порога FinchSpeak

Дата: 17 октября 2026. Проверенный код: 807a893 (опубликованный v1.1.0). Это результаты исследования и предложение дальнейшей работы, не отчёт об исправлении звука.

## Главный результат
Пользователь слышит клавиатуру и неудовлетворительное качество в **Test microphone / Hear myself**. Этот путь воспроизводит обработанный микрофон **до применения условия отправки**, без Opus, сети и приёмного jitter buffer. Поэтому изменение Speech threshold сейчас не убирает тихие звуки из местного прослушивания. Оно управляет отправкой собеседнику. Это подтверждено исходниками и отдельным экспериментом; причина плохого тембра конкретного микрофона пока не установлена.

`audio_engine.rs:715` записывает обработанный `capture_frame_48k` в mic test; строки720–727 кладут его в monitor queue независимо от VAD. `capture.rs:186–212` сначала обрабатывает PCM, затем решает, создавать ли сетевые пакеты. Приватность mic test остаётся закрытой: локальное воспроизведение не означает отправку на сервер.

Пользователь подтвердил, что **Hear myself и Test microphone работали одновременно**. По исходникам это действительно суммировало живой и записанный звук в локальном воспроизведении. Живое Hear myself само по себе имеет задержку и слышится вместе с собственным голосом. Эти режимы объясняют возможное эхо и наложение при проверке; причина неудовлетворительного тембра конкретного микрофона по-прежнему не установлена. Для сравнения тембра нужна отдельная запись без живого мониторинга.

## Проверенный эксперимент
Временный тест внутри существующего finch-audio, без установки зависимостей. 100 кадров тихого сигнала; одинаковый вход и состояния DSP, меняется только порог −70/−15 dBFS. Для изоляции именно порога использован Energy VAD; производственный Speech VAD имеет дополнительный нейросетевой детектор.

| Enhancement | Разрешена передача | Пакеты при −70 / −15 dB | Максимальная разность локального PCM |
|---|---|---|---|
| Off | Нет | 0 / 0 | 0 |
| Off | Да | 100 / 0 | 0 |
| On | Нет | 0 / 0 | 0 |
| On | Да | 100 / 0 | 0 |

Во всех четырёх случаях локальный PCM ненулевой. Тест PASS, 1.77s обработки, 3.43s компиляции. Временный код удалён с восстановлением исходного файла байт в байт; изменения продукта не внесены. Лог: рабочий worktree, `target/research/preview-threshold-probe.log`. Это не тест подавления реальной клавиатуры и не доказательство, что её не слышит собеседник.

## Проверка всех разделов присланного аудита

| № | Проверенное заключение |
|---|---|
|1. Дублирование DSP и размер кадров|Диагноз дублирования неверен. `aec.rs` оборачивает тот же native WebRTC AEC, `speech.rs` — классификатор речи, не EQ. Один AEC, один RNNoise, один gain stage. Кадры960 уже делятся на два480 внутри адаптеров. Переделка внешней очереди на10ms ради этого не требуется.|
|2. Native WebRTC|48kHz/max internal48k, HPF на AEC stage, AGC1 off, native NS off уже выставлены. Внешний float API принимает±1; WebRTC действительно переводит его во внутренний FloatS16, но вызывающий код уже не умножает вход повторно. Предлагаемые max gain25/initial6 — новая настройка, не исправление найденной ошибки; текущие12/0 более сдержанные. Transient suppression не включён данным bridge явно.|
|3. RNNoise|Преобразование в PCM16 уже есть:32767 перед вызовом, обратное деление после; отличие от32768 не объясняет субъективную проблему. Состояние сохраняется между кадрами; сбрасывается на границах приватности намеренно. Совету85/15 dry/wet нельзя следовать без временного выравнивания.|
|4. AEC/reference|При переполнении действительно очищается reference ring и сбрасывается AEC (`audio_engine.rs:585–596`), после чего нужна повторная адаптация. Однако переполнение ещё не доказывает drift: внешняя очередь регулярно полностью дренируется, причина может быть в задержке worker. Оценка output delay уже передаётся. Нужно измерить частоту underrun/overflow, render/capture timestamps и задержку прежде, чем писать свою коррекцию часов. Возможность отключать AEC для наушников полезна и поддерживается RFC7874.|
|5. VAD/гейт|Есть Earshot + RMS-порог,80ms pre-roll и100ms hangover. Понижение RMS-порога не обходит отрицательный ответ Earshot с фиксированным score0.5. Фронтенд отбрасывает `speaking` из mic-level event и показывает лишь RMS, что не даёт полного представления о решении VAD. Рекомендации60ms pre-roll и300ms hold не универсальное улучшение:60ms меньше нынешнего буфера; длинный hold может пропускать больше клавиатуры после речи.|
|6. EQ/лимитер в speech.rs|Описание файла ошибочно: там Earshot, не компрессор/эквалайзер. Фиксированные250Hz−2dB/3500Hz+1.5dB без записи конкретного микрофона не обоснованы. AGC2 уже имеет готовый limiter и выходной ceiling−1dBFS.|
|7. Opus|Уже48k mono/VoIP/64kbps, FEC on, ожидаемые потери5%, не0. Явные complexity/bandwidth/VBR настройки требуют проверки фактических defaults и A/B, но не объясняют дефект в локальном preview: оно не кодируется Opus. Постоянно завышать ожидаемые потери ради FEC не следует: это компромисс качества и устойчивости, не бесплатное улучшение.|
|8. Jitter/PLC/FEC|Адаптивный буфер2–6 кадров и Opus PLC уже есть; диагноз «потеря всегда заменяется нулями» неверен. Decode-FEC по следующему пакету действительно не реализован. Это полезный отдельный сетевой backlog, но не причина слышимого в Test microphone.|
|9. Mixer|Удалённые голоса суммируются с tanh, не с указанным в аудите hard clamp. Плавной рампы индивидуальной громкости нет — возможны щелчки при её смене. Tanh тоже нелинеен и заслуживает отдельного теста искажений. Локальные mic-test/monitor смешиваются отдельно; этот пункт не объясняет негейтированный preview.|
|10. Capture/resampler|Усреднение каналов подтверждено: интерфейс с одним активным из двух входов теряет6dB. Нужна явная политика mono/выбора входного канала; автоматическое переключение по RMS может давать нестабильный уровень. Открывается default config, не предпочтительный48k. Stateful FFT Rubato уже используется — обвинение в линейной/ступенчатой интерполяции неверно. Callback работают через предвыделенные ring buffer, общего подтверждения mutex/alloc обвинению нет.|
|11. Системный звук|Уже отдельный stereo Opus Application::Audio,96kbps и обход голосового DSP. Диагноз «моно/шумодав речи» неверен. SIGNAL_MUSIC можно оценить отдельно, но это hint выбора режима, не исправление описанной несуществующей цепочки.|
|12. Пользовательские настройки|Master Voice enhancement отключает выравнивание AGC2, а не RNNoise/AEC. Отдельных переключателей NS/AEC в UI нет. Это реальное ограничение для хорошего микрофона в тихой комнате. Нужны понятные профили/дополнительные настройки после A/B; десятки регуляторов и самописные фильтры противоречат запросу на простоту.|
|13. Приёмка|Нынешние три speech-файла — TTS-записи двух синтезаторов,16kHz/16bit/mono. Они не содержат исходной информации выше8kHz. Проверять на них сохранение8–12kHz невозможно. SNR/ERLE/пики/задержка полезны, но не заменяют естественность, согласные и прослушивание реального микрофона.|

## Почему часть предложений может ухудшить звук
- Слепой dry/wet85/15: у RNNoise в текущем стенде измерена задержка480samples/10ms. Смешивание с неделэированным dry даёт гребёнчатую окраску. Даже для идеальной задержанной копии амплитудная передача меняется от1 до0.7 (около−3.1dB) в зависимости от частоты. Нужны выравнивание и очистка обоих путей на privacy boundaries.
- Max gain25dB вместо12 может усилить остатки клавиатуры и дыхания, особенно в локальном негейтированном monitor. Само число не является доказанным улучшением.
- FEC не гарантируется одним ненулевым loss-percent: классическая FEC относится к LPC-слою Opus и зависит от режима/решения энкодера. Принудительная большая оценка потерь меняет распределение битрейта.
- Удаление reset RNNoise/AEC ради красивого старта фразы может вернуть ранее воспроизведённую регрессию утечки private PCM. Эти границы нужно сохранять при любом улучшении preview.

## Рекомендуемый порядок улучшений
1. **Сделать проверку микрофона достоверной.** Разделить просмотр обработанного микрофона и прослушивание с правилами активации; показать действительное решение VAD, а не только пересечение RMS-линии. Порог назвать порогом отправки. В режиме проверки разрешение сетевой передачи остаётся закрытым.
2. **Отделить измерение тембра от гейта.** На одной и той же48kHz записи сравнить исходник, AEC-only, RNNoise, AGC2 и их полный тракт с выровненными задержкой и уровнем. Отдельно проверить тихие согласные, окончания, дыхание, клавиатуру без речи и клавиатуру во время речи. Воспроизведение через Test microphone сейчас не доказывает проблемы Opus/сети.
3. **Сохранить готовые алгоритмы и минимум собственного DSP.** Сначала использовать существующие WebRTC AGC2/AEC3 и RNNoise; дать контролируемый способ сравнить NS on/off и AEC для наушников. Если именно RNNoise портит тембр на этих записях — сравнить с готовым WebRTC NS Moderate как альтернативой, с ровно одним шумодавом. Выбор default после A/B, без заранее назначенного25dB, EQ и85/15 mix.
4. **Улучшить приёмку.** Добавить реальные full-band записи и готовый offline ViSQOL в дополнение к существующим метрикам; сравнивать набор записей, не одну оценку. Проверить сам slider→backend→production Speech VAD, отдельный preview и отсутствие приватных пакетов при mic test/после выхода из него.
5. **Отдельный backlog:** FEC decode, плавная громкость собеседника, управление входными каналами интерфейса, предпочтение48k при поддержке устройства и измерение AEC reference. Их не смешивать с исправлением локального preview.

Для preview, имитирующего кодек, нужен отдельный приватный encoder/decoder либо строгий reset кодек-состояния: нельзя открыть реальный transmit gate или перенести в публичный Opus историю частной тестовой записи. Минимальный первый вариант — preview с теми же правилами активации и отдельной локальной историей, без изменения сетевого разрешения. Детальный дизайн изменений ещё не утверждён; продуктовый код в этом исследовании не менялся.

## Первичные источники
- [WebRTC RFC7874: AGC, clocks и AEC/headset](https://www.rfc-editor.org/rfc/rfc7874.html): рекомендует AGC для голоса и возможность отключения AEC/NLP, в том числе при наушниках. Это обоснование управления AEC, а не доказательство, что AEC вызвал данный дефект.
- [Официальные Opus encoder controls](https://opus-codec.org/docs/opus_api-1.5/group__opus__encoderctls.html): FEC/LPC, expected loss как компромисс, fullband как maximum bandwidth, SIGNAL как hint и complexity0–10. MAX_BANDWIDTH не гарантирует фактически выбранную полосу.
- [RNNoise, статья автора](https://web.jmvalin.ca/papers/rnnoise_mmsp2018.pdf):20ms overlap-add windows с10ms шагом; это не повод ломать960-sample транспортный контракт.
- [nnnoiseless source](https://docs.rs/crate/nnnoiseless/latest/source/src/lib.rs): тесты нормировки и пропуска первого выходного блока.
- [Google ViSQOL](https://github.com/google/visqol): готовая full-reference perceptual metric; audio mode48kHz, speech mode16kHz. Одна оценка не заменяет набор примеров/прослушивание. В runtime клиента добавлять инструмент не требуется.

## Экономия работы и границы результата
Две независимые проверки исходников делегированы gpt-6-luna: threshold/UI path и сверка13 разделов аудита. Основной агент перепроверил критичные выводы по исходникам и первичным источникам и выполнил короткий эксперимент; две неточности в первичном отчёте агента были исправлены. Пробная отдельная сборка агента остановлена, оставшиеся scratch Cargo процессы завершены; существующий target переиспользован для успешного теста. Точную денежную экономию без счётчика стоимости не заявляю.

v1.1.0 уже опубликован; CI39036540241, main candidate39036688554 и release39039298927 успешны. Все6 файлов скачаны,5SHA256 и подпись/tamper/manifest/offer повторно проверены. Прежний автоматический post-publication сценарий остановился на DNS github.com; полный public-runtime/anonymous-latest прогон не завершён. Тег не менялся. Для найденного поведения нужен отдельный проверенный патч; этот документ не объявляет субъективное качество исправленным.
