# QA 1.4.2 — качество демонстрации экрана

Дата: 2026-11-10. Ветка `feat/stream-quality`. Замеры сделаны на Windows 11, Intel Core i5-13400F (16 потоков), монитор 1920×1080 (180 Гц).

## Причины просадок (замер до правок)

`cargo run --release -p finch-client-core --example screen_bench -- 30`, 90 кадров:

| Стадия | Время на кадр | Бюджет при 30 FPS | Бюджет при 60 FPS |
| --- | --- | --- | --- |
| Захват (`xcap`, снимок на каждый кадр) | 42 мс | 33,3 мс | 16,7 мс |
| Подгонка размера и копия | 1,4 мс | | |
| RGBA → I420 | 2,2 мс | | |
| Кодирование OpenH264 (локальная сборка без NASM) | 70 мс | | |

Захват один ограничивал демонстрацию примерно 24 кадрами в секунду.

## Кодер и NASM

OpenH264 без NASM собирается без SIMD. Локальная сборка сделана без NASM, поэтому её замеры кодера
к релизным сборкам не относятся. На сборочной машине GitHub NASM предустановлен (`C:\Strawberry\c\bin\nasm.exe`), то есть релизы собираются с SIMD.

Задача `Encoder bench` (run 42801365322), синтетический «текстовый» экран со сдвигом, `encode_bench`:

| Картинка | Без NASM | С NASM |
| --- | --- | --- |
| 1920×1080, 30 FPS | 111,8 мс/кадр | 18,2 мс/кадр |
| 1920×1080, 60 FPS | 111,5 мс/кадр | 18,3 мс/кадр |
| 2560×1440, 30 FPS | 154,8 мс/кадр | 29,4 мс/кадр |

В режиме 30 FPS сборка с NASM уложилась в бюджет на этом тесте. В режиме 60 FPS среднее время кодирования составило 18,3 мс при бюджете 16,7 мс.
На такой случай есть автооткат на 30 FPS. Скорость кодера с NASM на машине замеров **не измерена**.
Настройки OpenH264 (число потоков, сложность, срезы) проверены на сборке без NASM и заметного выигрыша не дали.

## Захват после правок

`cargo run --release -p finch-screen --example wgc_bench`, 5 с, основной монитор:

| Условие | Кадров в секунду |
| --- | --- |
| Непрерывно перерисовываемое окно | 59,3 (297 кадров за 5,01 с) |
| Неподвижный экран | 0,2 (кадры приходят только при изменении картинки — так и задумано) |

На неподвижном экране ядро демонстрации пересылает последний кадр раз в секунду и по запросу ключевого кадра.

## Проверка между двумя клиентами

Два отладочных клиента 1.4.2 с отдельными профилями подключились к временному серверу 1.4.2 на localhost. Источник — тестовое окно 960×620. WebView получателя декодировал H.264 через WebCodecs. Все полученные видеокадры пришли в Tauri IPC как ArrayBuffer.

- **30 FPS, неподвижное окно.** Подписка через 1,2 секунды после старта, затем запрос ключевого кадра. Зритель получил 7 кадров, включая 2 ключевых, без ошибок декодера.
- **60 FPS, меняющееся окно.** Захват дал 56–59 кадров/с. Локальный кодер без NASM тратил 39–41 мс на кадр и отправлял 24–26 кадров/с. Режим переключился с 60 на 30 и отправил одно событие переключения. Зритель декодировал 160 кадров без ошибок.

Интерфейс покрыт тестами выбора 30/60, отображения статистики и уведомления о переходе на 30 FPS. У зрителя низкая частота кадров сама по себе больше не считается признаком проблем с соединением. Тест ядра проверяет, что закрытый источник завершает демонстрацию сразу.

## Автоматические проверки

Проверки запускаются командами `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo test --workspace --locked -- --test-threads=1`, `npm test` и `npm run build`. Windows-клиент собирается командой `cargo build --release --locked -p finch-app --features custom-protocol`. Скрипт `scripts/test-client-runtime.ps1` проверяет зависимости EXE и DLL. Локальная сборка использует готовые нативные библиотеки WebRTC.

## Открытые проверки

- Устойчивые 60 FPS, нагрузка на процессор и канал в релизной сборке с NASM.
- Запасной захват при недоступном WGC и поведение рамки на Windows 10.
- Свёрнутые окна и полноэкранные игры.
- Курсор на неподвижном экране. Если WGC не выдаёт новый кадр при движении только курсора, у зрителя его позиция обновится при следующем изменении картинки.
