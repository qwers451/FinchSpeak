# FinchSpeak (версия 3, QUIC). Полный план реализации

Самостоятельно хостируемый голосовой и текстовый мессенджер на Rust. Рассчитан на 10 одновременных пользователей, собственный VPS под управлением Linux Debian и нативный десктопный клиент на базе Tauri v2.

### 1.2. Обоснование выбора QUIC вместо WebRTC

1. **Сетевое соединение**: QUIC работает поверх одного UDP-сокета с встроенным шифрованием TLS 1.3. WebRTC требует поднятия связки протоколов SDP, ICE, STUN, TURN, DTLS и SRTP.
2. **Обход NAT**: Сервер размещен на VPS с белым статическим IP-адресом. Клиенты инициируют исходящее UDP-подключение к серверу, поэтому STUN и TURN серверы не требуются.
3. **Передача медиа**: Расширение QUIC Datagrams (RFC 9221) передает аудио и видео без ретрансляций в один системный вызов, а надежные потоки QUIC Streams параллельно доставляют текстовые сообщения и ключевые видеокадры.
4. **Смена сети**: При переключении ноутбука с Wi-Fi на проводную сеть QUIC мигрирует соединение по Connection ID без разрыва голосового сеанса.

## 3. Кастомный медиа-протокол поверх QUIC

### 3.1. Распределение трафика по каналам QUIC

1. **Канал управления (Control Channel)**: один двунаправленный поток (Bi-directional Stream 0). Обеспечивает надежную доставку с сохранением порядка. Передает авторизацию, вход в комнаты, текстовый чат, списки участников и запросы ключевых видеокадров.
2. **Канал ключевых видеокадров (Keyframe Stream)**: однонаправленные потоки (Uni-directional Streams). На каждый новый IDR-кадр открывается отдельный короткоживущий стрим, который закрывается сразу после передачи кадра.
3. **Канал медиа-датаграмм (QUIC Datagrams)**: ненадежная передача без ожидания потерянных пакетов. Передает голосовые фреймы Opus (20 мс), системный звук демонстрации экрана и нарезанные фрагменты дельта-кадров (P-frames) видео.

### 3.2. Формат управляющих сообщений (Control Stream)

Пакеты в потоке управления кодируются в формат MessagePack через крейт `rmp-serde`. Перед каждым сообщением записывается 4-байтный заголовок длины пакета в формате big-endian (`u32`).

#### Сообщения от клиента к серверу (`ClientMessage`):

1. `Authenticate`: содержит строковый JWT-токен `token`.
2. `JoinVoice`: содержит идентификатор канала `channel_id` (`Uuid`).
3. `LeaveVoice`: без параметров.
4. `UpdateVoiceState`: содержит флаги `muted` (`bool`) и `deafened` (`bool`).
5. `SendMessage`: содержит `channel_id` (`Uuid`), текстовое поле `content` и список идентификаторов загруженных файлов `attachments`.
6. `FetchHistory`: содержит `channel_id` (`Uuid`), метку времени `before` (`Option<i64>`) и лимит количества сообщений `limit` (`u32`).
7. `StartScreenShare`: содержит выбранный кодек (`H264`), ширину кадра `width` (`u32`), высоту `height` (`u32`) и частоту кадров `fps` (`u8`).
8. `StopScreenShare`: без параметров.
9. `SubscribeScreenShare`: содержит идентификатор стримера `target_user_id` (`Uuid`). Позволяет серверу пересылать видео только тем клиентам, которые открыли окно просмотра.
10. `UnsubscribeScreenShare`: содержит `target_user_id` (`Uuid`).
11. `RequestKeyframe`: содержит `target_peer_id` (`u32`). Отправляется зрителем при потере фрагментов дельта-кадра.
12. `Ping`: содержит локальную метку времени `timestamp` (`u64`).

#### Сообщения от сервера к клиенту (`ServerMessage`):

1. `Authenticated`: содержит `user_id` (`Uuid`), назначенный сервером короткий идентификатор сессии `session_peer_id` (`u32`), короткие идентификаторы всех каналов и полное начальное состояние сервера `initial_state`.
2. `Error`: содержит числовой код ошибки `code` (`u16`) и описание `message`.
3. `NewMessage`: содержит данные нового сообщения для отображения в чате.
4. `MessageHistory`: содержит массив исторических сообщений канала и флаг наличия более старых записей `has_more`.
5. `UserJoinedVoice`: содержит `user_id` (`Uuid`), назначенный ему `peer_id` (`u32`), имя пользователя и идентификатор канала.
6. `UserLeftVoice`: содержит `user_id` (`Uuid`), `peer_id` (`u32`) и идентификатор канала.
7. `UserVoiceStateChanged`: содержит `peer_id` (`u32`), флаги `muted` и `deafened`.
8. `ScreenShareStarted`: содержит `user_id` (`Uuid`), `peer_id` (`u32`), параметры видеопотока.
9. `ScreenShareStopped`: содержит `peer_id` (`u32`).
10. `KeyframeRequested`: команда стримеру принудительно сгенерировать IDR-кадр для зрителей.
11. `PresenceUpdate`: содержит `user_id` (`Uuid`) и новый статус (онлайн, отошел, не беспокоить, оффлайн).
12. `Pong`: возвращает `timestamp` (`u64`) из запроса клиента.

*Серверное сообщение VoiceActivity полностью исключено из протокола. Клиент вычисляет факт речи участника локально в момент поступления от него аудио-датаграмм.*

### 3.3. Формат медиа-датаграмм (20 байт заголовок)

```text
┌──────────┬──────────┬──────────┬──────────┬──────────┬──────────┬──────────┐
│ Тип (1Б) │ Канал(4Б)│ Отпр.(4Б)│ Номер(2Б)│ Метка(4Б)│ Кадр(2Б) │Фрагм.(3Б)│
└──────────┴──────────┴──────────┴──────────┴──────────┴──────────┴──────────┘
```

Поля заголовка `MediaHeader` (все многобайтовые числа передаются в порядке big-endian):

1. `media_type` (1 байт, смещение 0):
   - `0x01`: Голосовой фрейм Opus (20 мс).
   - `0x02`: Ключевой кадр видео H.264 IDR (используется в заголовке Uni-Stream).
   - `0x03`: Дельта-кадр видео H.264 (передается в датаграммах).
   - `0x04`: Системный звук трансляции экрана Opus (20 мс).
2. `channel_id` (4 байта, `u32`, смещение 1..5): короткий числовой идентификатор голосового канала.
3. `sender_peer_id` (4 байта, `u32`, смещение 5..9): сессионный идентификатор отправителя. При отправке с клиента заполняется своим `session_peer_id`. Сервер принудительно проверяет и перезаписывает сюда реальный `session_peer_id` отправителя перед рассылкой пакета остальным участникам.
4. `sequence` (2 байта, `u16`, смещение 9..11): монотонно растущий порядковый номер пакета.
5. `timestamp` (4 байта, `u32`, смещение 11..15): временная метка в сэмплах (шаг 960 единиц на пакет для звука 48 кГц, частота 90 кГц для видео).
6. `frame_id` (2 байта, `u16`, смещение 15..17): порядковый номер видеокадра. Для аудио всегда равен `sequence`.
7. `fragment_index` (1 байт, `u8`, смещение 17): индекс текущего фрагмента внутри видеокадра (начиная с 0). Для аудио всегда 0.
8. `total_fragments` (1 байт, `u8`, смещение 18): общее количество фрагментов в текущем кадре. Для аудио всегда 1.
9. `flags` (1 байт, `u8`, смещение 19): битовая маска. Бит 0 (`0x01`) указывает на последний голосовой пакет перед наступлением тишины. Бит 1 (`0x02`) указывает на включенное сквозное шифрование (E2EE) полезной нагрузки.

Максимальный размер полезной нагрузки после заголовка составляет 1160 байт. Общий размер датаграммы не превышает 1180 байт.

### 3.4. Фрагментация видео и защита от рассинхронизации

1. **Отправка ключевого кадра (IDR)**: энкодер генерирует кадр размером 30-80 КБ вместе с заголовками параметров SPS и PPS. Клиент открывает новый однонаправленный поток QUIC, записывает в него 20-байтный `MediaHeader` с типом 2 и номером `frame_id`, затем записывает тело кадра и закрывает поток.
2. **Отправка дельта-кадра (P-frame)**: энкодер генерирует кадр размером от 1 до 15 КБ. Модуль `fragmenter.rs` делит буфер кадра на части по 1160 байт. Каждая часть получает общий номер `frame_id`, свой индекс `fragment_index` и общее число частей `total_fragments`, после чего отправляется отдельной QUIC-датаграммой.
3. **Сборка и синхронизация на приемнике**:
   - Приемник хранит буфер сборки для текущего `frame_id`. Когда все части от 0 до `total_fragments - 1` получены, буфер склеивается в единую NAL-единицу и передается в декодер.
   - Если хотя бы один фрагмент дельта-кадра не пришел в течение 40 мс, кадр отбрасывается целиком, а клиент отправляет на сервер команду `RequestKeyframe`.
   - **Правило блокировки при чтении ключевого кадра**: как только клиент обнаруживает открытие входящего однонаправленного стрима с новым IDR-кадром, он выставляет флаг ожидания ключевого кадра. Пока этот стрим не дочитан до конца и IDR-кадр не передан в декодер, все приходящие по датаграммам дельта-кадры с меньшим или промежуточным `frame_id` отбрасываются.

## 4. Аудио-пайплайн

### 4.1. Таблица рабочих параметров звукового тракта

1. **Частота дискретизации внутри пайплайна**: строго 48 000 Гц (частота работы DeepFilterNet и Opus).
2. **Частота захвата и вывода cpal**: нативная частота операционной системы (44 100 Гц, 48 000 Гц, 96 000 Гц) с автоматической конвертацией через полифазный ресемплер `rubato`.
3. **Размер рабочего окна**: 20 мс (960 сэмплов при 48 000 Гц, моно, формат `f32`).
4. **Алгоритм эхоподавления**: WebRTC AEC3 (обработка блоками по 10 мс внутри обертки 20 мс).
5. **Битрейт кодека Opus**: адаптивный от 32 до 96 кбит/с, режим VoIP, встроенная коррекция ошибок In-band FEC включена.
6. **Размер пакета Opus в сети**: ~160 байт при битрейте 64 кбит/с (плюс 20 байт `MediaHeader`).

### 4.2. Захват, сведение и ресемплинг (`capture.rs` и `resampler.rs`)

1. Вызывается метод `default_input_config` на выбранном устройстве ввода.
2. Поток открывается с родным числом каналов (например, 2 канала) и родной частотой (например, 44 100 Гц).
3. В функции обратного вызова `cpal` стерео-сэмплы суммируются и делятся пополам для получения моно-сигнала, после чего записываются в неблокирующий кольцевой буфер `ringbuf`.
4. Рабочий аудио-поток вычитывает сэмплы из кольцевого буфера. Если родная частота отличается от 48 000 Гц, данные проходят через ресемплер `FftFixedInOut` из крейта `rubato`, который выдает ровно 960 сэмплов каждые 20 мс.
5. Аналогичный обратный процесс (из 48 000 Гц в родную частоту наушников и дублирование моно-сигнала в правый и левый каналы) выполняется в модуле `playback.rs` перед выводом звука.

### 4.3. Подавление акустического эха и шума (`aec.rs` и `noise.rs`)

1. Поток воспроизведения после микширования голосов всех участников записывает копию выходного 960-сэмплового буфера в отдельный кольцевой буфер референсного сигнала.
2. Перед обработкой микрофона модуль `aec.rs` вычитывает 960 сэмплов референса и передает их вместе с 960 сэмплами микрофона в процессор `webrtc-audio-processing` (с разбивкой на два подфрейма по 480 сэмплов, так как алгоритм WebRTC работает окнами по 10 мс). Эхо вычитается из микрофонного сигнала.
3. Очищенный от эха фрейм поступает в модуль `noise.rs`. При высоком профиле качества работает нейросеть DeepFilterNet. Если время обработки превышает 8 мс, движок автоматически переключается на легковесный алгоритм RNNoise (крейт `nnnoiseless`).
4. После шумоподавления модуль `vad.rs` вычисляет среднеквадратичную громкость (RMS) в децибелах (dBFS). Если уровень превышает порог пользователя, фрейм кодируется в Opus и уходит в сеть. При окончании фразы отправляется еще 5 фреймов (100 мс) плавного затухания, причем последний пакет помечается флагом конца речи (бит 0 в поле `flags` заголовка).

### 4.4. Адаптивный Jitter Buffer с расширением счетчика (`jitter.rs`)

1. Для каждого участника хранится счетчик циклов переполнения (rollover counter) и последнее полученное 16-битное значение `last_seq`.
2. При приходе нового пакета со значением `seq` вычисляется знаковая 16-битная разность: `delta = seq.wrapping_sub(last_seq) as i16`.
3. Полный 64-битный индекс пакета вычисляется прибавлением `delta` к предыдущему 64-битному индексу. Очередь пакетов хранится в структуре `BTreeMap` с ключом `u64`.
4. Целевая задержка буфера адаптируется в диапазоне от 40 мс (2 пакета) до 120 мс (6 пакетов) на основе вариации времени прихода пакетов (RFC 3550).
5. Если в момент вызова функции чтения нужный пакет еще не дошел по сети, вызывается декодер Opus с пустым буфером (режим Packet Loss Concealment), который синтезирует плавное продолжение звука на основе предыдущего фрейма.

### 4.5. Микширование и локальная индикация речи (`mixer.rs`)

1. Декодированные фреймы умножаются на индивидуальный множитель громкости участника (от 0.0 до 2.0) и складываются в выходной массив из 960 элементов `f32`.
2. К итоговому буферу применяется функция мягкого насыщения (лимитер): `x = x.tanh()`.
3. **Локальный детектор речи**: когда из сети приходит аудио-датаграмма от участника `sender_peer_id`, микшер фиксирует текущее время для этого участника. Если участник молчал, отправляется событие начала речи в UI. Если нет пакетов дольше 250 мс или пришел пакет с флагом конца речи, подсветка гаснет. Сервер в этом не участвует.

## 5. Демонстрация экрана и рендеринг через WebCodecs

### 5.1. Схема передачи видео без локального HTTP-сервера и без fMP4

1. Захватчик (`xcap` или Windows Graphics Capture API) получает кадр в формате BGRA с частотой 30 или 60 кадров в секунду.
2. Конвертер цветовых пространств переводит кадр в формат NV12 или I420.
3. Аппаратный кодировщик H.264 (NVENC на картах NVIDIA, Media Foundation на Windows, VAAPI на Linux, с автоматическим откатом на `openh264`) сжимает кадр в NAL-единицу (Annex B `00 00 00 01`).
4. Модуль фрагментации отправляет IDR-кадры через QUIC Uni-Stream, а P-кадры нарезает в QUIC Datagrams.
5. Сервер SFU пересылает видеопоток только тем клиентам, которые прислали сообщение `SubscribeScreenShare`.
6. Клиент-зритель собирает фрагменты кадра в буфер и проверяет целостность.
7. Собранный сжатый H.264 кадр передается напрямую из Rust в Webview через бинарный канал Tauri v2 (`tauri::ipc::Channel`) в виде `Uint8Array`.
8. В коде фронтенда (`ScreenViewer.tsx`) данные принимает `VideoDecoder` WebCodecs API, который декодирует кадр на GPU и мгновенно отрисовывает `VideoFrame` на элементе Canvas через контекст 2d (`drawImage`) или WebGL.

### 5.2. Преимущества WebCodecs + Tauri Channel

1. Задержка 50-100 мс (в отличие от 800-1500 мс в MSE).
2. В клиентском Rust-ядре отсутствуют декодер видео, fMP4-мультиплексор и локальный HTTP-сервер.
3. Декодирование на GPU потребляет <2% CPU.

### 5.3. Захват системного звука при трансляции

1. **Windows**: WASAPI Loopback через `cpal` (захват устройства вывода по умолчанию).
2. **Linux**: PipeWire через крейт `pipewire`.
3. Звук демонстрации экрана кодируется отдельным Opus-энкодером в стерео (96 кбит/с, режим Audio) и отправляется датаграммами с типом `MediaType::ScreenAudio` (4).

## 6. Серверная логика SFU и защита от подмены отправителя

### 6.1. Сессионные идентификаторы (`session_peer_id`)

1. Всем каналам из базы SQLite назначаются короткие 32-битные номера (`u32`).
2. При аутентификации сервер инкрементирует `AtomicU32` и выдает клиенту `session_peer_id`.
3. Связка между соединением `quinn`, UUID пользователя и `session_peer_id` фиксируется в `DashMap`.

### 6.2. Безопасная маршрутизация пакетов в SFU

1. Проверяется длина пакета (не менее 20 байт).
2. Сервер извлекает верифицированный `auth_peer_id` (`u32`) и комнату отправителя.
3. Если пользователь не в канале или принудительно заглушен, пакет отбрасывается.
4. Сервер перезаписывает байты с индекса 5 по 8 (`sender_peer_id`) значением `auth_peer_id` (big-endian).
5. Для `Audio` (1): сервер рассылает датаграмму всем участникам канала, кроме отправителя и `deafened`.
6. Для `VideoDelta` (3), `ScreenAudio` (4) и Uni-Streams `VideoKey` (2): сервер рассылает данные только подписчикам трансляции.

## 9. Отказоустойчивость, сеть и адаптация к потерям

### 9.1. Миграция соединения и переподключение

1. `quinn`: `max_idle_timeout` = 15с, `keep_alive_interval` = 4с.
2. При смене IP связь сохраняется без переподключения сокета благодаря QUIC Connection ID.
3. При разрыве более 15с: экспоненциальный бэкофф (500мс * 2 до 15с + джиттер 300мс) с авто-аутентификацией и перезаходом в голосовой канал.

### 9.2. Адаптивный битрейт и обработка потерь

1. Приёмник считает потери каждые 3с по пропускам в 64-битном счётчике.
2. Потери > 5% -> сообщение о деградации канала -> Opus снижает битрейт до 32 кбит/с, включает In-band FEC, устанавливает `packet_loss_perc` 15%.
3. При потере дельта-кадра зритель шлёт `RequestKeyframe`. Сервер агрегирует запросы (не более 1 `KeyframeRequested` в секунду стримеру).

## 10. Безопасность и сквозное шифрование (E2EE)

### 10.1. TOFU (Trust On First Use)

Сервер генерирует Ed25519 сертификат и выводит SHA-256 отпечаток. Клиент сохраняет отпечаток при первом подтверждении и проверяет при повторных подключениях.

### 10.2. Сквозное шифрование (E2EE)

1. Обмен ключами X25519 в комнате, выработка симметричного ключа Room Key (256 бит).
2. Заголовок `MediaHeader` (20 байт) передаётся открытым, флаг `0x02` (E2EE).
3. Payload шифруется ChaCha20-Poly1305. Nonce (12 байт) = `sender_peer_id (4B) + timestamp (4B) + sequence (2B) + frame_id (2B)`.
4. AAD = 20-байтный `MediaHeader`. Клиент заполняет `sender_peer_id` своим `session_peer_id`, так что после SFU заголовок идентичен и проверка Poly1305 проходит.
